# Поиск пунктов норм (RAG)

К замечанию проверки прикладывается пункт нормы с дословной цитатой: статья и часть закона, пункт ГОСТ или СП. Цитата сверяется с исходным текстом документа в корпусе. Если такой цитаты в документе нет, пункт к замечанию не прикладывается.

## Корпус

`data/norm_corpus/`, индекс `index.json`:
- 52 документа: 223-ФЗ, 102-ФЗ, ГК РФ ч. 2, ТР ТС 011/2011, 29 ГОСТ, 14 СП, 5 СНиП;
- 13 775 фрагментов: 12 989 пунктов и 786 таблиц.

Как режется текст:
- законы делятся по частям статей: «Статья 3, ч. 6.1» для ФЗ, «Статья 475, п. 2» для ГК;
- стандарты делятся по пунктам с иерархией разделов;
- пункт длиннее 1400 символов режется на окна, каждое окно остаётся точной подстрокой пункта.

Статус стандарта берётся из справочника Росстандарта проекта (`refdata`): 1 252 фрагмента «Действует», 122 «Заменён», у остальных запись не найдена. Для заменённого стандарта в замечание пишется замена, а замечание уходит на ручную проверку.

## Набор вопросов

`eval/rag/questions_v2.json`, 421 вопрос (`eval/rag/build_questions.py`):

| Набор | С ответом | Без ответа | Откуда эталон |
|---|---:|---:|---|
| замечания правил на 2 образцах и 9 ТЗ из ЕИС | 242 | 80 | статья из `norm_ids` замечания и стандарт, названный в тексте |
| 105 экспертных правок (99 после удаления дублей) | 77 | 22 | ручная разметка: какая статья или какой стандарт должны прийти |

«Без ответа» означает, что нужной нормы в корпусе нет: внутренний стандарт заказчика, ОКПД 2, противоречие внутри ТЗ. В таких случаях правильно отказать. В наборе правил есть перекос: 129 вопросов ведут к 223-ФЗ ст. 4 ч. 10.

## Поиск по всему корпусу

Метрики считаются без подсказки статьи. Если в тексте назван стандарт, поиск ограничен этим документом (`eval/rag/run_eval.py`, `metrics_v2.json`). Recall@k и MRR@10 даны по пункту, «Док R@k» по документу. Время указано на вопрос на GPU, без загрузки модели; у гибрида это сумма BM25 и эмбеддингов.

| Метод | R@1 | R@5 | R@10 | MRR@10 | Док R@1 | Док R@5 | Правки R@1 | Правки MRR | с/вопрос |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| BM25 (леммы pymorphy3) | 0,179 | 0,235 | 0,408 | 0,218 | 0,345 | 0,599 | 0,078 | 0,122 | 0,020 |
| эмбеддинги deepvk/USER-bge-m3 | 0,119 | 0,210 | 0,238 | 0,156 | 0,176 | 0,270 | 0,078 | 0,138 | 0,014 |
| эмбеддинги BAAI/bge-m3 | 0,107 | 0,207 | 0,248 | 0,142 | 0,163 | 0,292 | 0,078 | 0,112 | 0,008 |
| **гибрид BM25 + USER-bge-m3 (RRF)** | **0,194** | **0,345** | **0,414** | **0,250** | 0,285 | 0,511 | 0,182 | 0,207 | 0,034 |
| гибрид BM25 + bge-m3 (RRF) | 0,141 | 0,310 | 0,392 | 0,210 | 0,257 | 0,517 | 0,091 | 0,149 | 0,028 |
| гибрид USER-bge-m3 + реранкер bge-reranker-v2-m3 (топ-20) | 0,194 | 0,288 | 0,361 | 0,236 | 0,270 | 0,389 | 0,221 | 0,235 | 0,310 |

Отказ: оценка лучшего фрагмента почти не отделяет вопросы без ответа. При лучшем пороге сбалансированная точность у всех методов от 0,50 до 0,52: почти случайный уровень. Поэтому поиску по всему корпусу без опоры на статью или стандарт верить нельзя. Пороги записаны в `tzcheck/rag/models.py` (`REFUSE`).

## Как работает в отчёте проверки

Путь замечания (`tzcheck/rag/__init__.py`, `evidence_for`):

1. В `norm_ids` указана статья закона: приходит эта статья, нужная часть и подпункт «N)», если он назван.
2. В тексте назван стандарт: приходит пункт этого стандарта. Если замечание о статусе самого стандарта (заменён, лишняя или пропущенная «Р»), приходит пункт «Область применения».
3. Иначе поиск по всему корпусу, только для замечаний о конкуренции, стандартах и гарантии. Найденный так пункт помечается «проверить применимость», замечание уходит на ручную проверку.

Замер этого пути (`eval/rag/prod_eval.py`, `prod_metrics.json`):

| Режим | Правила: пункт верный | Правила: отказ без ответа | Правки: пункт верный | Правки: пункт неверный | Правки: отказ без ответа | с/замечание, CPU |
|---|---:|---:|---:|---:|---:|---:|
| BM25, без поиска по корпусу | 242 / 242 | 80 / 80 | 2 / 77 | 0 | 22 / 22 | 0,09 |
| BM25 + поиск по корпусу | 242 / 242 | 80 / 80 | 3 / 77 | 1 | 22 / 22 | 0,07 |
| **гибрид + поиск по корпусу** | 242 / 242 | 80 / 80 | **12 / 77** | 1 | 22 / 22 | 0,21 |

**Режим по умолчанию:** гибрид BM25 + deepvk/USER-bge-m3 с поиском по корпусу (`TZCHECK_RAG_OPEN=auto`). Основания:
- лучший R@5 и MRR на всех наборах;
- на правках приложен верный пункт к 12 из 77 замечаний против 2–3 у BM25, неверный один (12 из 13);
- на замечаниях правил все режимы дают одинаковый результат.

Если torch или векторы не установлены, поиск сам переходит на BM25, а поиск по корпусу выключается.

Реранкер в режим по умолчанию не входит. R@1 у него такой же, как у гибрида, R@5 хуже, а каждый вопрос стоит ещё 0,28 с на GPU. Выигрыш только на правках по R@1: 0,221 против 0,182. Включается флагом `TZCHECK_RAG_MODE=rerank`.

ai-forever/FRIDA в сравнение не вошла: сборка её векторов занимала больше 14 ГБ RAM, и процесс был остановлен.

Проверено на образцах (`TZCHECK_RAG=1`, режим по умолчанию, CPU):
- `samples/lift_src.docx`: пункт нормы с цитатой есть у 12 из 18 замечаний. Примеры: «2) в описание предмета закупки не должны включаться требования или указания в отношении товарных знаков…» (223-ФЗ, ст. 3, ч. 6.1); ГОСТ Р 53782-2010, п. 1 «Область применения»; ГК РФ, ст. 471, п. 4;
- `samples/metro_src.docx`: пункт нормы есть у 85 из 93 замечаний;
- первая проверка после запуска грузит модель эмбеддингов (около 1,4 ГБ RAM), дальше гибрид добавляет к проверке документа доли секунды на замечание;
- в HTML пункт показан в блоке «Основание вывода», в DOCX в комментарии: «Пункт нормы: …: «цитата»».

## Запуск

```
TZCHECK_REFDATA_OFFLINE=1 python -m tzcheck.rag build                       # индекс BM25
python -m tzcheck.rag.models build --model deepvk/USER-bge-m3 --device cuda  # векторы, около 190 с на GPU
TZCHECK_RAG=1 python -m tzcheck samples/lift_src.docx -o out
python eval/rag/build_questions.py && python eval/rag/run_eval.py --rerank --device cuda && python eval/rag/prod_eval.py --modes bm25,hybrid --open
```

Модели качаются в `HF_HOME`. Векторы лежат в `data/norm_corpus/vectors/` и привязаны к sha256 индекса: после пересборки индекса векторы со старым отпечатком не загружаются.

GPU при сборке векторов загружен в среднем на 13,5 % (пауза после каждой пачки, `TZCHECK_RAG_GPU_DUTY=0.6`). При замере средняя загрузка 16 %. Выше 70 % было 10 % пятисекундных отсчётов, на кодировании вопросов.

## Ограничения

- В корпусе 52 документа. Нормы, которых в нём нет, система не процитирует, а откажет.
- Разметку правок делал один разметчик.
- Вопросы из правил наследуют `norm_ids` правил: проверяется, что приходит нужный пункт, а не верность самой ссылки правила.
- Для 90 % фрагментов стандартов статус в справочнике не найден, в отчёте они идут как «не проверен».
