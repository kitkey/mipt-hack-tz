# Разбор PDF и OCR сканов

Замер прежней версии на правилах, её код удалён 14.11.2026; текущая проверка моделью описана в README.

## Что поддерживается

- **Текстовый PDF** разбирается по текстовому слою (`tzcheck/parse.py`), разбор понимает абзацы, таблицы, ячейки, объединённые по вертикали, и таблицы через разрыв страницы.
- **Скан**, то есть PDF без текстового слоя, или картинка (PNG, JPG, TIFF, в том числе многостраничный, BMP) распознаётся PaddleOCR PP-OCRv5, lang=ru (детектор `PP-OCRv5_mobile_det`, распознавание `eslav_PP-OCRv5_mobile_rec`, `tzcheck/ocr.py`). OCR включается сам, если установлен `requirements-ocr.txt` (`TZCHECK_OCR=auto`). К каждой распознанной странице в отчёт добавляется предупреждение "скан без текстового слоя, текст распознан OCR (PaddleOCR): цифры и коды сверить с оригиналом".

Что делается со сканом до правил:
1. Снимается наклон страницы, угол берётся по медиане верхних кромок длинных строк и не больше 10°.
2. По линиям сетки (морфология OpenCV) находятся таблицы. Текст раскладывается по ячейкам, и объединённая по вертикали ячейка повторяется в каждой строке, как в разборе DOCX.
3. Абзацы вне таблиц и строки внутри ячейки собирает тот же код, что и для текстового PDF. Он склеивает переносы слов и разорванные коды ОКПД 2 (`26.51.62.11` + `0` → `26.51.62.110`).
4. Слова со смешанным алфавитом приводятся к одному алфавиту. Латинские двойники в русских словах меняются на кириллицу ("ha" → "на", "chип" → "снип", "ШT." → "ШТ."), кириллица в латинских брендах на латиницу ("RIGОL" → "RIGOL"). Латинские слова без смешения (RIGOL, BINDER) не меняются.
5. Распознавание идёт в отдельном процессе. Paddle на CPU с MKLDNN изредка падает с segfault, тогда процесс перезапускается, и страница распознаётся заново. За прогон 116 страниц так случилось один раз, страница прошла со второй попытки.

## Набор

В наборе четыре пары DOCX/PDF (lift_src, metro_src, lift_fin, metro_fin), всего 29 страниц. В `generated/` лежит каждая страница в 150 и 300 dpi в двух видах.
- чистая;
- искажённая (поворот 1–3°, шум, серый фон, JPEG, печать и подпись).

Всего картинок 116, список лежит в `manifest.json`. Искажения синтетические, реальных сканов из ЕИС в наборе нет.

## 1. Текстовый PDF против DOCX

`benchmark_text.py` → `results_text.json`:
- CER и WER считаются как расстояние Левенштейна на всём тексте документа после приведения регистра и пробелов;
- ячейки, числа и коды ОКПД 2 сравниваются как мультимножества;
- замечания получены `check(..., use_llm=False)` на DOCX и на PDF, совпадением считается та же категория при сходстве цитат не ниже 0,7.

| Пара | Стр. | CER | WER | Ячейки | Числа | ОКПД 2 | Замечания: совпало / в DOCX / в PDF |
|---|---:|---:|---:|---:|---:|---:|---:|
| lift_src | 7 | 0,48 % | 0,43 % | 187 / 188 | 163 / 163 | 1 / 1 | 18 / 18 / 18 |
| metro_src | 6 | 1,09 % | 1,17 % | 205 / 214 | 280 / 280 | 28 / 28 | 92 / 93 / 93 |
| lift_fin | 7 | 0,46 % | 0,40 % | 192 / 193 | 179 / 179 | 2 / 2 | 7 / 7 / 7 |
| metro_fin | 9 | 0,06 % | 0,15 % | 286 / 292 | 368 / 368 | 53 / 53 | 8 / 8 / 9 |

Раньше CER metro_src был 23 %. Разбор DOCX повторяет объединённую по вертикали ячейку в каждой строке таблицы, потому что это нужно правилам. Так в metro_src 14 раз повторяется адрес МФТИ, а в PDF он напечатан один раз, и разбор PDF его не повторял. Из-за этого не срабатывали правила по строкам с этой ячейкой. Теперь разбор PDF повторяет такую ячейку и в пределах страницы, и через разрыв страницы (`_rows_fill_vmerge`). CER упал с 23,03 % до 1,09 %, замечаний совпадает 92 из 93 вместо 86.

Расхождения, которые остались на metro_src:
- в DOCX рамка с текстом "В составе заявки… точную модель и страну происхождения…" сделана таблицей из одной ячейки, а в PDF это абзац. На абзаце срабатывает лишнее замечание "Лишнее в ТЗ";
- на PDF не сработало одно замечание "Ограничение конкуренции" по позиции "ТПУ-01".

## 2. OCR по страницам

`run_ocr.py` → `results_ocr.json`. Эталоном каждой страницы служит текстовый слой той же страницы PDF. CER и WER чувствительны к порядку строк, поэтому рядом дан recall слов без учёта порядка. Замер шёл на CPU, 4 потока, MKLDNN, paddlepaddle 3.1.1. Тексты распознавания лежат в `ocr_text/`.

| Страницы | Стр. | CER | WER | Слова | Числа | ОКПД 2 | Медиана, с/стр. |
|---|---:|---:|---:|---:|---:|---:|---:|
| 150 dpi, чистые | 29 | 1,06 % | 2,5 % | 97,9 % | 98,1 % | 100 % | 6,0 |
| 150 dpi, искажённые | 29 | 1,77 % | 3,8 % | 96,5 % | 96,9 % | 100 % | 5,6 |
| 300 dpi, чистые | 29 | 2,40 % | 6,2 % | 94,5 % | 96,0 % | 100 % | 9,0 |
| 300 dpi, искажённые | 29 | 2,09 % | 4,7 % | 95,9 % | 95,9 % | 100 % | 8,6 |

Что дали правки:
- снятие наклона: на искажённых страницах 1–3 lift_src CER был от 4 до 39 %, после правки от 1,3 до 4,2 %. На повёрнутой странице строки перемешивались при группировке;
- замена латинских двойников: CER 300 dpi чистых упал с 2,65 % до 2,40 %, recall слов вырос с 93,2 % до 94,5 %.

На 300 dpi результат хуже, чем на 150. Модель распознавания чаще путает короткие слова с латиницей и чаще режет строки. Поэтому PDF-сканы рендерятся в 200 dpi (`TZCHECK_OCR_DPI`).

Время:
- первая страница после запуска занимает около 60 с при свободном диске, потому что загружаются Paddle и модели (около 100 МБ);
- следующие идут по 2–10 с на страницу на CPU.

Пробы, которые не взяты:
- paddlepaddle 3.3.1 с MKLDNN падает (ошибка PIR onednn), без MKLDNN 57–117 с на страницу, поэтому взят 3.1.1;
- детектор `PP-OCRv5_server_det` дал на первой странице CER 0,54 % против 0,58 % у mobile, но на второй странице процесс упал с segfault, поэтому по умолчанию стоит mobile.

GPU не использовался.

## 3. Скан целиком через проверку

PDF без текстового слоя собран из картинок 300 dpi и проверен целиком (`check(scan.pdf, use_llm=False)`). Замечания сравниваются с проверкой DOCX.

| Скан | Стр. | CER к DOCX | Числа | ОКПД 2 | Замечания: совпало / в DOCX / на скане | Было до разметки таблиц | с на документ |
|---|---:|---:|---:|---:|---:|---:|---:|
| lift_src, чистый | 7 | 1,29 % | 156 / 163 | 1 / 1 | 15 / 18 / 17 | 7 / 18 | 51–242 |
| lift_src, искажённый | 7 | 1,55 % | 159 / 163 | 1 / 1 | 12 / 18 / 18 | 7 / 18 | 51 |
| metro_src, чистый | 6 | 10,6 % | 276 / 280 | 28 / 28 | 63 / 93 / 83 | 12 / 93 | 53 |
| metro_src, искажённый | 6 | 11,5 % | 271 / 280 | 28 / 28 | 63 / 93 / 78 | 19 / 93 | 51 |

Время первого документа включает загрузку Paddle (242 с при занятом другими процессами диске).

Что дала разметка скана:
- раньше каждая строка OCR шла отдельным абзацем, таблицы терялись, на metro_src совпадало 12–19 замечаний из 93;
- после разбора сетки таблиц, сборки абзацев, склейки ячеек и замены двойников совпадает 63 из 93, коды ОКПД 2 находятся все 28 из 28 вместо 12–14.

Почему на metro_src не 93:
- CER 10–11 % набирается в основном из-за порядка строк. В DOCX пункты внутри ячейки идут отдельными абзацами ("• Микрометр… – 2 шт."), а на скане ячейка склеена в одну строку. Правила полноты, которые срабатывают на отдельный пункт списка, на склеенной ячейке не срабатывают (около 20 из 30 пропусков);
- регистр сокращений: OCR читает "СИ" как "Си", "МГц" как "мГц". Правило про поверку не узнаёт оговорку "при отнесении к СИ" и даёт лишние замечания "Стандарты" по позициям 4–14;
- отдельные буквы в брендах путаются между алфавитами. "RIGОL", "НIОКI" теперь чинятся, но правило про конкуренцию на позиции Осциллографа всё равно не сработало из-за склейки ячейки.

## Запуск

```
pip install -r requirements-ocr.txt          # paddlepaddle 3.1.1, paddleocr 3.4.0
PADDLE_PDX_CACHE_HOME=<каталог моделей> TZCHECK_REFDATA_OFFLINE=1 python -m tzcheck scan.pdf -o out
python eval/ocr_compare/benchmark_text.py    # текстовый PDF против DOCX
python eval/ocr_compare/run_ocr.py           # 116 страниц и сканы целиком
python eval/ocr_compare/run_ocr.py --rescore # пересчёт по сохранённым текстам
```

Переменные:
- `TZCHECK_OCR=auto|1|0`;
- `TZCHECK_OCR_DET=mobile|server`;
- `TZCHECK_OCR_DEVICE=cpu|gpu`;
- `TZCHECK_OCR_DPI=200`;
- `TZCHECK_OCR_THREADS=8`;
- `TZCHECK_OCR_MKLDNN=1`;
- `TZCHECK_OCR_ISOLATE=1` (отдельный процесс распознавания).

## Ограничения

- Сканы синтетические, это страницы своих же PDF с наложенными искажениями. Реальные сканы ЕИС с плохой печатью, рукописными пометками и таблицами без линий сетки не проверялись.
- Таблица находится только по линиям сетки (нужен OpenCV из `requirements-ocr.txt`). Таблица без рамок распознаётся как текст с разделителем " | ".
- Пункты списка внутри ячейки на скане не разделяются, поэтому правила по отдельным пунктам срабатывают реже, чем на DOCX.
- Числа и коды после OCR нужно сверять с оригиналом, это написано в предупреждении отчёта.
