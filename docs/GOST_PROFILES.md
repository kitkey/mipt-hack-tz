# Чеклисты ГОСТ: интерфейс для ядра проверки

Модуль `tzcheck/gost_profiles.py`. Чеклист стандарта (профиль) собирает модель при первой встрече стандарта, дальше он берётся из кэша `<справочники>/gost_profiles/<slug>.json`: в Docker это том `refdata` (`/refdata/gost_profiles`), туда же пишутся утверждения, и они переживают перезапуск; локально `tzcheck/data/gost_profiles`. Каталог можно задать `TZCHECK_GOST_PROFILES`. Собранные профили поставляются в `tzcheck/data/gost_profiles` и при старте докладываются в том, если их там нет; профили в томе не перезаписываются. Сопоставление ТЗ с чеклистом делает ядро: модуль отдаёт пункты для позиции и ничего не сверяет с текстом ТЗ сам.

## Статусы пункта

| Статус | Что значит | Где виден |
|---|---|---|
| `draft` | выписала модель, сверку с текстом ГОСТ не прошёл (не совпало, пример, справочное, рекомендация, отменён) | только в профиле, поле `drafts`, с причиной |
| `verified` | сверен моделью с текстом ГОСТ: полный пункт, область применения, заголовки разделов над пунктом и соседние пункты; совпадают параметр, оператор, число, единица; это требование, не отменён | `items_for` |
| `approved` | утвердил человек (`approved_by`, `approved_at`) | `items_for` |

Как ядру выставлять важность, решает ядро. Договорённость с владельцем: противоречие пункту `approved` для этого вида изделия идёт ошибкой с пунктом ГОСТ и цитатой; противоречие пункту `verified` идёт на проверку; параметра из чеклиста нет в ТЗ: всегда на проверку, заказчик не обязан переписывать стандарт.

## items_for(position, passport, complete=None) -> list[dict]

```python
from tzcheck.gost_profiles import items_for

items = items_for(
    {"name": "Работы по замене грузового лифта", "kind": "лифт грузовой", "okpd2": "43.29.19.120", "description": "..."},
    {"gosts": ["ГОСТ 33984.1-2023", "ГОСТ Р 55964-2022"]},
)
```

`position`: `name` обязателен; `kind` (вид изделия), `okpd2` (строка или список), `description` по желанию.
`passport`: `gosts`, обозначения стандартов, на которые ссылается ТЗ, как в тексте ТЗ («ГОСТ Р 34441-2018» найдёт текст ГОСТ 34441-2018, если стандарта с «Р» нет).
`complete`: функция модели `prompt -> dict` для тестов; по умолчанию `llm._call` с `TZCHECK_LLM_*`.

Применимость стандарта к позиции решает модель по разделу «Область применения»: один вызов на (slug, вид изделия), ответ кэшируется в `_applicability.json` и сбрасывается при смене текста стандарта. Вид изделия берётся из `kind`, без него из `name`. Без модели незакэшированная применимость не решается, и функция возвращает пустой список.

Стандарт пропускается, если текста нет или профиль не собран; для отчёта об этом конвейер уже выпускает отметки «не проверено» (`gost_profile.unavailable`, `gost_profile.not_built`). Повторы между стандартами слиты: на одно требование одна запись, основания в `sources`.

Поля записи:

| Поле | Что |
|---|---|
| `cid` | id канонического пункта |
| `slug`, `designation` | стандарт главного основания (утверждённое раньше сверенного) |
| `clause`, `clause_text` | номер пункта и полный текст пункта стандарта |
| `quote` | цитата, по которой выписан пункт |
| `kind` | `order_param` (что заказчик указывает при заказе), `limit` (предел), `docs` (документ или маркировка при поставке) |
| `param`, `aliases`, `requirement` | параметр, как он может называться в ТЗ, требование своими словами |
| `operator`, `op` | для `limit`: «не менее», «не более», «от ... до», «равно», «одно из» и код `min`, `max`, `range`, `eq`, `one_of`; иначе `null` |
| `value`, `unit` | для `limit`: число, `[min, max]` для `range`, список для `one_of`; значение не числом («IP 2XC», «600 x 800») строкой, как в стандарте; единица как в стандарте |
| `form` | для `docs`: «документ» или «маркировка» |
| `applies_to` | `{"product", "variant", "conditions"}` из сверки: к какому виду, исполнению и условиям относится пункт |
| `condition` | условие применимости одной строкой (пусто, если пункт для всей продукции) |
| `status` | `approved`, если хоть одно основание утверждено, иначе `verified` |
| `sources` | все основания: `slug`, `designation`, `clause`, `clause_text`, `quote`, `item_id`, `status`, `approved_by`, `approved_at`, `applies_to`, `condition`, `applicability` (`why`, `quote` решения о применимости) |

## Утверждение

```python
from tzcheck.gost_profiles import approve
approve("gost-33984-1-2023", ["gost-33984-1-2023#12"], "Иванов И. И.")          # verified -> approved
approve("gost-33984-1-2023", ["gost-33984-1-2023#12"], "Иванов И. И.", revoke=True)
```

Черновик утвердить нельзя, он вернётся в `skipped` с причиной. Утверждение переживает пересборку профиля, если текст стандарта тот же и модель выписала тот же пункт.

HTTP (роутер модуля подключён в `tzcheck/api.py`):
- `GET /api/gost_profiles`: профили с числом пунктов по статусам (`by_status`) и видам (`by_kind`);
- `GET /api/gost_profiles/{slug}`: обзорные поля профиля, `scope_text` (область применения), `items` (чеклист) и `drafts` (черновики, утверждать нельзя). У каждого пункта `id`, `kind`, `kind_title`, `param`, `requirement`, `condition`, `limit` (как в профиле: `op`, `min`, `max`, `values`, `unit`), `form`, `clause`, `quote` (цитата из ГОСТ), `nature`, `applies_to`, `status`, `status_title`, `approved_by`, `approved_at`, `verify_reason` (довод сверки моделью), `draft_reason` (почему черновик), `can_approve`; 404 без профиля;
- `POST /api/gost_profiles/{slug}/approve`, тело `{"item_ids": [...], "user": "...", "revoke": false}`: 404 без профиля, 400 без пользователя.

CLI: `python -m tzcheck.gost_profiles build "ГОСТ 34441-2018" [--force] | --all`, `list`, `approve <slug> <id>... --by "Иванов"`, `merge`, `lexicon --out lexicon_gost.jsonl`.
