# API для интерфейса проверки ТЗ

Описание для фронта: какие вызовы нужны экранам 1-5, что отправлять и что приходит в ответ. Сервер: FastAPI (`tzcheck/api.py`, новые маршруты в `tzcheck/api_ui.py`), по умолчанию `http://<host>:8000`. Авторизации нет. Все ответы JSON в UTF-8, кроме скачивания файлов и потока SSE.

## Какой экран каким вызовом пользуется

| Экран | Что делает | Вызовы |
|---|---|---|
| Форма 1, загрузка | «+» добавляет до 10 файлов (первый файл основное ТЗ, остальные приложения); выбор проверок; запуск | `GET /api/meta` (группы, названия шагов, есть ли модель), `POST /api/jobs` |
| Форма 1, «Сопоставить требования» | текущее ТЗ против прошлого документа | `POST /api/jobs` с полем `previous` (ход по шагам) или `POST /api/requirements_compare` (синхронно) |
| Форма 1, шестерёнка | нормативная база: список, просмотр, догрузка, удаление | `GET /api/norms`, `GET /api/norms/{id}`, `GET /api/norms/{id}/file`, `POST /api/norms`, `DELETE /api/norms/{id}`, `GET /api/norms/search` |
| Форма 2, ход проверки | шаги конвейера с состоянием и счётчиками | `GET /api/jobs/{job_id}/events` (SSE), запасной вариант `GET /api/jobs/{job_id}` раз в 1-2 с |
| Форма 3, результат | общая оценка, число замечаний, три группы, список, выгрузки, «Внести предлагаемые изменения» | `GET /api/runs/{run_id}` (или поле `result` готовой задачи), файлы по ссылкам из `links`, решения по замечаниям `POST /api/feedback` |
| Форма 4, «Новая проверка» | сброс формы 1 | своих вызовов нет |
| Форма 5, история | карточки по времени; карточка открывается как форма 3 | `GET /api/runs`, затем `GET /api/runs/{run_id}` |

`job_id` и `run_id` всегда совпадают: одна задача = один запуск = одна папка с файлами.

## Группы и выбор проверок

| Ключ `checks` | Группа | Категории замечаний |
|---|---|---|
| `logic` | Логика | Противоречие; Неполнота или комплектность; Некорректная характеристика; Лишнее в ТЗ; Предмет закупки или наименование |
| `standards` | Стандарты | Стандарты (ГОСТ, поверка); Неверный или общий код ОКПД 2; Оформление по внутреннему стандарту |
| `risks` | Риски | Ограничение конкуренции; Гарантийные условия |

- `checks` не передан, пустой или `all` → полная проверка (все три группы).
- Можно передать списком (`checks=logic&checks=risks`) или строкой через запятую (`checks=logic,risks`), в query или в форме.
- Работают только правила выбранных групп, промпт модели получает только категории выбранных групп, сверка частей документа моделью (только «Противоречие» и «Предмет закупки») без логики не вызывается.
- Неизвестный ключ → `400 {"error": "checks: неизвестные группы ..."}`.
- «Спорные требования, нужна ручная проверка» это статус замечания (`status: "ручная проверка"`), а не группа: он бывает в любой группе.

Если проверялась не вся группа: `full_check: false`, `verdict` и `summary` начинаются с фразы «Проверка неполная: проверены только группы ..., вывод о готовности ТЗ к публикации по такой проверке не делается», а `verdict_code` вместо `clean` будет `partial`.

## Полнота проверки: состояние шагов

Каждый шаг конвейера в результате получает состояние (`steps_status`):

| `state` | Когда |
|---|---|
| `выполнен` | шаг прошёл без сбоев |
| `неприменим` | шаг не нужен при этих настройках: модель не подключена или не допущена к документу, группа не выбрана, нет замечаний для повторной проверки |
| `не выполнен` | шаг не дошёл до конца: исчерпан бюджет времени модели, нет OCR для скана, шаг не запускался |
| `ошибка` | шаг упал: правило выбросило исключение, фрагмент модели пропущен из-за ошибки, проверка профилей ГОСТ упала |

```json
"steps_status": [
  {"id": "parse", "title": "Разбор документа", "state": "выполнен", "reason": ""},
  {"id": "rules", "title": "Проверка правилами", "state": "ошибка", "reason": "правило check_x упало: ..."},
  {"id": "llm_find", "title": "Модель ищет замечания по фрагментам документа", "state": "неприменим", "reason": "модель не подключена"}
],
"completeness": {"complete": false, "all_groups": true, "all_steps": false, "incomplete_steps": ["rules"]}
```

- `completeness.complete` = все группы выбраны и ни один шаг не в состоянии `ошибка` или `не выполнен`.
- Если хоть один шаг `ошибка` или `не выполнен`: `status: "incomplete"` (вместо `ok`), `summary` и `verdict` начинаются с «Проверка неполная: «<шаг>» (<состояние>: <причина>)», а при пустом списке замечаний `verdict_code: "incomplete"` (не `clean`). Фраз «явных проблем не найдено» и «можно публиковать» в таком заключении нет. Результат при этом полный по форме: замечания, отчёты и ссылки на месте.
- При пустом списке замечаний заключение называет позиции без профиля характеристик (их свойства правилами не сверялись): «Не проверялись по профилям характеристик позиции без профиля (4): Плита поверочная гранитная; ...».
- Для интерфейса `status` `ok` и `incomplete` оба означают «результат есть»; `error` = документ не разобран.

## Открытый документ (`public`)

Флаг `public` (`1/0`, `true/false`) в `/check`, `/api/check`, `/api/jobs`, `/api/requirements_compare`: документ открытый, например уже опубликован в ЕИС. Флаг попадает в проверку как признак документа (`doc.public`); по нему решается, можно ли отправлять текст во внешнюю модель без слоя NER. В результате поле `public`. По умолчанию `false`.

## Форма 1-2: задачи

### POST /api/jobs

`multipart/form-data`. Ответ `202`.

| Поле | Тип | Обязательно | Смысл |
|---|---|---|---|
| `file` | файл | да | основное ТЗ: docx, doc, rtf, odt, pdf (в том числе скан), картинка, xlsx, txt |
| `attachments` | файлы, повторяющееся поле | нет | приложения; вместе с `file` не больше 10 |
| `previous` | файл | нет | прошлый документ: если передан, задача делает «Сопоставить требования» (`kind: "requirements_compare"`) |
| `use_llm` | `1/0`, `true/false` | нет, по умолчанию `true` | использовать модель; если модель не настроена, всё равно `false` |
| `orchestrator` | `linear` / `graph` | нет, `linear` | `graph`: тот же конвейер на LangGraph с повторной проверкой замечаний с низкой уверенностью |
| `checks` | см. выше | нет | группы проверок |
| `user` | строка | нет | имя пользователя для истории (до 120 символов) |
| `public` | `1/0`, `true/false` | нет, `false` | документ открытый (например, из ЕИС), см. выше |

Поля можно передавать в форме или в query (`/api/jobs?use_llm=false&checks=risks`).

```json
{"job_id": "871f5ff20a73", "run_id": "871f5ff20a73", "kind": "check", "status": "running", "use_llm": false,
 "orchestrator": "linear", "checks": ["logic", "standards", "risks"],
 "links": {"self": "/api/jobs/871f5ff20a73", "events": "/api/jobs/871f5ff20a73/events", "result": "/api/runs/871f5ff20a73"}}
```

Ошибки: `400` (неизвестный `orchestrator` или `checks`, больше 10 файлов).

### GET /api/jobs/{job_id}

Параметр `result=false` убирает тяжёлое поле `result`.

```json
{
  "job_id": "871f5ff20a73", "run_id": "871f5ff20a73", "kind": "check", "status": "done",
  "created_at": "2026-11-14T16:59:02", "started_at": "2026-11-14T16:59:02", "finished_at": "2026-11-14T16:59:04",
  "user": "Иванова", "files": ["lift_src.docx"], "checks": ["logic", "standards", "risks"],
  "progress": {"done": 6, "total": 6, "percent": 100, "current": null, "current_title": null, "current_text": ""},
  "steps": [
    {"id": "parse", "title": "Разбор документа", "status": "done", "started_at": "2026-11-14T16:59:02", "finished_at": "2026-11-14T16:59:02",
     "seconds": 0.3, "details": {"blocks": 163, "files": 1}, "text": "блоков разобрано: 163"},
    {"id": "rules", "title": "Проверка правилами", "status": "done", "seconds": 1.3, "details": {"findings": 19}, "text": "замечаний: 19", "...": "..."},
    {"id": "report", "title": "Выгрузка отчёта, файла с комментариями и файла с правками", "status": "done", "details": {"revisions": 9}, "text": "правок в файле: 9", "...": "..."}
  ],
  "error": null, "result_url": "/api/runs/871f5ff20a73",
  "result": { "...": "тот же объект, что GET /api/runs/{run_id}, без полей run и decisions" }
}
```

- `status` задачи: `queued`, `running`, `done`, `error`.
- `status` шага: `pending`, `running`, `done`, `skipped`, `not_done`, `error`; то же по-русски в поле `state`: `ожидает`, `идёт`, `выполнен`, `неприменим`, `не выполнен`, `ошибка`. Причина сбоя в `details.ошибка` или `details.причина` и в `text`.
- `text` шага уже собран по-русски из `details`, его можно показывать как есть.
- После перезапуска сервиса ход задачи в памяти пропадает: готовая задача отдаётся из сохранённого отчёта (`steps: []`, `status: "done"`), незавершённая получит `status: "lost"`.
- Неизвестный id → `404`.

`GET /api/jobs` отдаёт список задач текущего процесса (без результата). У `GET /api/jobs`, `GET /api/jobs/{id}` и `/events` есть параметр `user`, правила видимости как у истории (см. форму 5).

### Шаги

Шаги берутся из конвейера (`pipeline.check`, `graph.check_graph`), выдуманных шагов нет. Набор зависит от настроек: план приходит первым событием.

| id | Название | Когда есть | `details` |
|---|---|---|---|
| `parse` | Разбор документа | всегда | `blocks`, `files` |
| `security` | Поиск скрытых символов и инструкций для ИИ | всегда | `warnings` |
| `rules` | Проверка правилами | всегда | `findings` |
| `llm_verify_rules` | Модель перепроверяет спорные замечания правил | с моделью | `candidates`; по ходу `batch`, `batches`, `items`; в конце `findings` |
| `llm_find` | Модель ищет замечания по фрагментам документа | с моделью | по ходу `fragment`, `fragments`, `found`; `stage` при сверке частей документа; в конце `found` |
| `llm_verify_new` | Независимая перепроверка находок модели | с моделью | `candidates`, `batch`/`batches`, в конце `confirmed`, `findings` |
| `llm_recheck` | Повторная проверка замечаний с низкой уверенностью | граф с моделью; `skipped`, если таких замечаний нет | `candidates`, `findings` |
| `reconcile` | Сверка требований между разделами | всегда | `found` |
| `reconcile_llm` | Модель сверяет похожие требования | с моделью, если выбрана Логика | `found` |
| `finish` | Итог: профили ГОСТ, решения закупщиков, уверенность, заключение | всегда | `findings` (основной список), `model`, `unchecked` |
| `report` | Выгрузка отчёта, файла с комментариями и файла с правками | всегда | `revisions` (сколько правок внесено) |
| `check_old` | Проверка прошлого документа | сопоставление | по ходу `inner` (какой шаг идёт у прошлого документа), в конце `findings` |
| `req_pairing` | Сопоставление требований двух документов | сопоставление | `pairs: {old, new, unchanged, changed, added, removed}` |

Рассуждения модели в ход не попадают (они выключены, `TZCHECK_LLM_REASONING=off`), передаются только счётчики.

### GET /api/jobs/{job_id}/events (SSE)

`Content-Type: text/event-stream`. Подключение через `new EventSource(url)`.

| event | data | Когда |
|---|---|---|
| `snapshot` | то же, что `GET /api/jobs/{id}?result=false` | сразу после подключения |
| `plan` | `{"steps": [шаг, ...]}` | план шагов (приходит 1-3 раза: шаги задачи и шаги конвейера) |
| `step` | один шаг (как в `steps`) | шаг начался, закончился, пропущен или обновились счётчики |
| `done` | `{"job_id", "status": "done", "result_url", "summary"}` | задача готова, поток закрывается |
| `error` | `{"job_id", "status": "error", "error"}` | задача упала, поток закрывается |

У событий `plan`, `step`, `done`, `error` есть `id:` (порядковый номер). Переподключение без повторов: `?after=<последний id>` или заголовок `Last-Event-ID` (EventSource шлёт его сам). Раз в 15 с без событий приходит комментарий `: keep-alive`.

Ход на `samples/lift_src.docx` без модели:

```
event: snapshot      {"status": "running", "progress": {"done": 0, "total": 6, "current": "parse", ...}, "steps": [...]}
id: 1  event: plan   {"steps": [{"id": "report", ...}]}
id: 2  event: plan   {"steps": [{"id": "parse"}, {"id": "security"}, {"id": "rules"}, {"id": "reconcile"}, {"id": "finish"}, {"id": "report"}]}
event: step  parse running
event: step  parse done 0.3 с      блоков разобрано: 163
event: step  security done 0.0 с   предупреждений: 0
event: step  rules done 1.3 с      замечаний: 19
event: step  reconcile done 0.0 с  найдено замечаний: 0
event: step  finish done 0.1 с     замечаний: 18; не проверено: 3
event: step  report done 0.1 с     правок в файле: 9
event: done  {"status": "done", "result_url": "/api/runs/871f5ff20a73", "summary": "Публиковать без исправлений нельзя: ..."}
```

С моделью между `rules` и `reconcile` идут `llm_verify_rules`, `llm_find` (с событиями `step` по каждому фрагменту: «фрагмент 3 из 12; найдено замечаний: 5»), `llm_verify_new`.

## Форма 3: результат

### GET /api/runs/{run_id}

Полный результат (тот же формат, что у `POST /api/check`) плюс карточка запуска, ссылки и решения закупщика.

```json
{
  "run_id": "871f5ff20a73", "file": "lift_src.docx", "status": "ok", "mode": "rules", "model": "", "orchestrator": "linear", "public": false,
  "steps_status": [{"id": "parse", "title": "Разбор документа", "state": "выполнен", "reason": ""}, "..."],
  "completeness": {"complete": true, "all_groups": true, "all_steps": true, "incomplete_steps": []},
  "steps": ["parse", "security", "rules", "reconcile"], "seconds": 1.6,
  "checks": ["logic", "standards", "risks"], "check_groups": ["Логика", "Стандарты", "Риски"], "full_check": true,
  "verdict": "Публиковать без исправлений нельзя: ошибок высокого риска 3 (F003, F004, F005). Ещё высокого риска на ручную проверку 2 (F001, F002).",
  "verdict_code": "blocked",

                          "by_category": {"Противоречие": 4, "Неполнота или комплектность": 1, "Предмет закупки или наименование": 1}},
               "Стандарты": {"...": "..."}, "Риски": {"...": "..."}},
    "by_category": {"...": 0}, "by_severity": {"high": 5, "medium": 7, "low": 6}, "by_status": {"ошибка": 5, "...": 0},
    "needs_review": 8, "revisions": 9,
    "model_block": {"count": 0, "by_severity": {}, "by_category": {}, "by_group": {}},
    "unchecked_block": {"count": 3, "by_rule": {"gost.old_unverified": 1, "...": 1}},
    "confidence": {"...": 0}
  },
  "findings": [ "...замечания, см. ниже..." ],
  "norms": {"ROSSTANDART": {"title": "Росстандарт, сведения о действии стандартов", "text": "...", "url": "https://..."}},
  "warnings": [], "pii_masked": {}, "document": {"format": "docx", "files": ["lift_src.docx"], "blocks": 163, "fields": {}, "requirement_graph": {}},
  "passport": {"справочники": {}, "файлы": [], "модель": "не подключена"},
  "revisions": {"main": {"applied": ["F003", "F004", "..."], "skipped": {}, "file": "lift_src.revisions.docx"}},
  "links": {
    "report_json": "/runs/871f5ff20a73/lift_src.report.json",
    "report_html": "/runs/871f5ff20a73/lift_src.report.html",
    "comments_docx": "/runs/871f5ff20a73/lift_src.comments.docx",
    "revisions_docx": "/runs/871f5ff20a73/lift_src.revisions.docx",
    "result": "/api/runs/871f5ff20a73"
  },
  "run": { "...карточка, как в GET /api/runs..." },
  "decisions": {"F004": {"decision": "accept", "comment": "заменим", "ts": "2026-11-14T17:01:06"}}
}
```

Что показать на форме 3:
- общая оценка: `verdict_code` (цвет) и `verdict` (текст);
- количество замечаний: `stats.by_group` в сумме (основной список) или `findings.length` с разбивкой по `section`;
- детализация по трём группам: `stats.groups` (у непроверенной группы `checked: false`);
- подробный список: `findings` (основной список `section: "main"`, отдельными блоками `llm_review` и `unchecked`, в вердикт они не входят);
- выгрузки: «отчёт» `links.report_html` или `links.report_json`, «файл с комментариями» `links.comments_docx`;
- «Внести предлагаемые изменения»: `links.revisions_docx`. Ссылки нет, если в документе нет ни одного замечания с точной заменой или исходник не DOCX: кнопку тогда не показывать.

Ошибка `404 {"error": "run not found"}` (в том числе, если запуск скрыт правилами видимости истории). Параметр `user` как у `GET /api/runs`.

### Поля замечания

| Поле | Тип | Смысл |
|---|---|---|
| `id` | строка | `F001...` основной список, `M001...` замечания модели, `U001...` «не проверено» |
| `group` | `Логика` / `Стандарты` / `Риски` | группа интерфейса, вычисляется по категории |
| `category` | строка | категория кейса (одна из 10) |
| `severity` | `high` / `medium` / `low` | риск |
| `status` | `ошибка` / `неясно` / `ручная проверка` / `рекомендация` | статус; «ручная проверка» = спорное требование, бывает в любой группе |
| `needs_review` | bool | нужна ручная проверка |
| `section` | `main` / `llm_review` / `unchecked` | блок отчёта |
| `confidence` | число 0-1 | внутренняя уверенность правила |
| `confidence_pct`, `confidence_basis` | число 0-100 или `null`, строка | оценка модели и на чём она основана; у правил `null` и «правило» |
| `quote` | строка | точная цитата из документа; пустая у замечаний на документ в целом |
| `location` | строка | место по-русски: «раздел «4. Место и сроки выполнения работ.», абзац 21» или «таблица 1, строка 31» |
| `block_id` | строка | id блока документа (`p21`, `t1r31`; у приложений префикс `a1_`) |
| `also_in` | список id блоков | то же замечание в других местах |
| `explanation` | строка | почему это проблема |
| `fix` | строка | как исправить (рекомендация словами) |
| `replacement` | строка | точный текст, которым заменяется `quote` в файле с правками; пусто, если замены нет |
| `norm_ids` | список | основания, расшифровка в `result.norms[id]` (`title`, `text`, `url`, `edition`) |
| `evidence` | объект | основание вывода: статус по каталогу, пункт нормы с цитатой, вторая проверка моделью и т.п. |
| `source`, `rule_id` | строка | кто нашёл: правило (`rule:gost`, `days.in_words`) или модель (`llm`, `llm.find`) |

Пример:

```json
{"id": "F015", "group": "Стандарты", "category": "Оформление по внутреннему стандарту", "severity": "low", "status": "рекомендация",
 "needs_review": false, "section": "main", "confidence": 0.8, "confidence_pct": null, "confidence_basis": "правило",
 "quote": "105 календарных дней", "location": "раздел «4. Место и сроки выполнения работ.», абзац 21", "block_id": "p21", "also_in": [],
 "explanation": "Срок указан только цифрами; по практике закупщиков заказчика сроки дублируются прописью, чтобы исключить опечатку в цифре.",
 "fix": "105 (сто пять) календарных дней", "replacement": "105 (сто пять) календарных дней", "norm_ids": ["INTERNAL"],
 "evidence": {"практика заказчика": "МФТИ: сроки цифрами и прописью (...)", "найдено": "rule:days"}, "source": "rule:days", "rule_id": "days.in_words"}
```

### Файл с правками (`<base>.revisions.docx`)

Копия исходного DOCX, где каждое замечание с `replacement` внесено правкой в режиме рецензирования (`w:del` / `w:ins`, автор «Проверка ТЗ»), к правке приложен комментарий с номером замечания. Word и LibreOffice показывают правки как исправления, их можно принять или отклонить по одной. Правкой становятся только замены, которые правило знает точно:

| Правило | Пример |
|---|---|
| ГОСТ заменён (по каталогу Росстандарта) | `ГОСТ Р 34441-2018` → `ГОСТ 34441-2024` |
| «ГОСТ» без «Р» и лишняя «Р» | `ГОСТ 53782-2010` → `ГОСТ Р 53782-2010` |
| срок прописью | `105 календарных дней` → `105 (сто пять) календарных дней` |
| единое начало сроков | `с момента заключения` → `с даты заключения` |
| марка без «или эквивалент» | `кнопки BW-1-круглые` → `кнопки BW-1-круглые (или эквивалент)` |
| «мкр» вместо «мкм», документация на английском, начало гарантии «с даты приёмки» | по тексту рекомендации правила |

Всё остальное (добавить характеристику, перечислить стандарты, замечания модели) остаётся комментарием в `comments.docx`. Список внесённых и пропущенных правок: `result.revisions.main.applied` / `skipped`. Для приложений DOCX: `attachment_<i>.revisions.docx` (ссылки `links.attachment_<i>_revisions_docx`).

### POST /api/feedback (решение закупщика, без изменений)

```json
{"run_id": "871f5ff20a73", "finding_id": "F004", "decision": "accept", "comment": "заменим"}
```

`decision`: `accept` (принято), `reject` (отклонено), `review` (ручная проверка). Решения видны в `GET /api/runs/{id}` (`decisions`) и в карточке истории (`run.decisions`).

## «Сопоставить требования»

Текущее ТЗ сравнивается с другим документом (например, прошлогодним ТЗ на тот же предмет). Это не `/compare` (версии одного документа до и после правок). Требования (позиции и характеристики из строк таблиц, пункты разделов) сводятся попарно по сходству текста без модели; номер позиции в первой ячейке не учитывается, перенумерация изменением не считается. По текущему документу идёт полная проверка (или выбранные группы), прошлый документ проверяется так же, чтобы найти повторяющиеся ошибки.

### POST /api/requirements_compare

`multipart/form-data`: `old` (прошлый документ), `new` (текущее ТЗ), `attachments` (приложения текущего ТЗ, необязательно), `use_llm` (по умолчанию `false`), `orchestrator`, `checks`, `user`, `public`. Ответ синхронный; для формы 2 с ходом по шагам использовать `POST /api/jobs` с `file` = текущее ТЗ и `previous` = прошлый документ, тогда этот же объект лежит в `result.requirements_compare`.

```json
{
  "status": "ok", "run_id": "7a2b9d330153", "old_file": "lift_src.docx", "new_file": "lift_fin.docx",
  "summary": "Требований в прошлом документе 145, в текущем 152: без изменений 135, изменено 10, новых 7, убрано 0. Замечаний по текущему документу 10: ошибка повторяется с прошлого документа 7, на изменённых требованиях 0, на новых 1, ...",
  "requirements": {
    "counts": {"old": 145, "new": 152, "unchanged": 135, "changed": 10, "added": 7, "removed": 0},
    "changed": [{"similarity": 0.766, "kind": "характеристика",
                 "old": {"block_id": "t1r2", "kind": "характеристика", "location": "раздел «Технические характеристики ...», таблица 1, строка 2", "section": "...", "label": "Тип лифта", "value": "пассажирский | 1", "text": "1 | Тип лифта | пассажирский"},
                 "new": {"block_id": "t1r2", "label": "Тип лифта", "value": "грузовой | 1", "text": "1 | Тип лифта | грузовой", "...": "..."},
                 "diff": [{"op": "заменено", "было": "пассажирский", "стало": "грузовой"}]}],
    "added": [{"block_id": "t2r3", "kind": "позиция", "text": "2 | Грузовой лифт | шт. | 1 | 28.22.16.112", "...": "..."}],
    "removed": []
  },
  "findings_summary": {
    "repeated": [{"id": "F001", "group": "Риски", "category": "Ограничение конкуренции", "quote": "...", "location": "...", "old_finding_id": "F003", "old_location": "..."}],
    "on_changed": [], "on_added": [{"id": "F007", "...": "..."}], "other_count": 2,
    "not_repeated_from_old": [{"id": "F004", "...": "замечания прошлого документа, которых в текущем нет"}],
    "summary": "..."
  },
  "old_check": {"file": "lift_src.docx", "summary": "...", "stats": {}, "findings": []},
  "links": {"revisions_docx": "/runs/7a2b9d330153/lift_fin.revisions.docx", "requirements_compare_json": "/runs/7a2b9d330153/req_compare.json", "...": "..."},
  "result": { "...полная проверка текущего документа, как GET /api/runs/{run_id}..." }
}
```

- `kind` требования: `позиция` (строка таблицы с единицей измерения), `характеристика` (другая строка таблицы), `пункт раздела` (абзац).
- `diff[].op`: `заменено`, `удалено`, `добавлено`.
- `repeated`: замечание текущего документа, у которого в прошлом документе есть замечание той же категории на той же цитате или на парном требовании («ошибка повторяется»).

## Шестерёнка: нормативная база

### GET /api/norms

```json
{
  "documents": [
    {"id": "int-65fa43320fdb", "kind": "internal", "document": "СТО Лифты 07-2026", "status": "внутренний стандарт заказчика", "customer": "МФТИ",
     "uploaded_at": "2026-11-14T17:00:45", "file": "sto_lift.docx", "blocks": 6, "characters": 486, "deletable": true, "edition": "", "source": "загружен через интерфейс: sto_lift.docx", "title": "СТО Лифты 07-2026"},
    {"id": "customer-mipt", "kind": "customer_practice", "document": "Практика закупщиков: МФТИ", "deletable": false, "...": "..."},
    {"id": "fz-223", "kind": "corpus", "document": "223-ФЗ", "edition": "ред. ...", "status": "...", "deletable": false, "...": "..."}
  ],
  "counts": {"internal": 1, "customer_practice": 1, "corpus": 54, "edition": 17},
  "references": [{"id": "223-FZ-3-6.1-2", "title": "223-ФЗ, ст. 3, ч. 6.1, п. 2", "text": "...", "url": "...", "edition": "..."}],
  "index": {"fresh": true, "path": "..."}
}
```

`kind`: `internal` (загруженные внутренние стандарты, удаляются), `customer_practice` (правила практики заказчика из `customers.json`), `corpus` (законы и стандарты корпуса), `edition` (тексты новых редакций от обновлятора). `references` это короткая база оснований, на которую ссылаются `norm_ids` замечаний.

### GET /api/norms/{id}

Карточка документа плюс `text` (весь текст) и `blocks_list` (`[{"type": "text"|"table", "text": "..."}]`). Работает и для `references` (id вида `223-FZ-3-6.1-2`). `404`, если нет.

`GET /api/norms/{id}/file` отдаёт исходный загруженный файл (только `internal`).

### POST /api/norms

`multipart/form-data`: `file` (docx или pdf; также doc, rtf, odt, txt), `title` (название, по умолчанию имя файла), `customer` (заказчик, по умолчанию «заказчик»). Ответ `201`:

```json
{"id": "int-65fa43320fdb", "kind": "internal", "document": "СТО Лифты 07-2026", "customer": "МФТИ", "deletable": true,
 "chunks": 3, "index_rows": 16028, "auto_numbered": false, "...": "..."}
```

Документ разбирается тем же парсером, что ТЗ, и индексируется в корпус поиска норм; каждый его пункт в индексе помечен `customer` и `internal: true`. Пункты без нумерации нумеруются при загрузке (`auto_numbered: true`). Пересборка индекса занимает 10-20 с, запрос ждёт её. Ошибки: `400` (формат, пустой файл, нет текста), `409` (документ с таким названием или тот же файл уже есть). Наружу ничего не отправляется.

### DELETE /api/norms/{id}

Только для `internal`: `{"deleted": "<id>"}`; документы корпуса и практику удалить нельзя (`403`), нет такого (`404`). Индекс пересобирается.

### GET /api/norms/search?q=...&limit=5&internal_only=false

Поиск пунктов по корпусу (BM25), для проверки загруженного стандарта и окна просмотра.

```json
{"query": "антивандальное зеркало закалённое стекло кабина",
 "items": [{"document": "СТО Лифты 07-2026", "number": "1.2", "title": "...", "text": "1.2. Кабина лифта оснащается антивандальным зеркалом ...",
            "quote": "Кабина лифта оснащается антивандальным зеркалом из закалённого стекла толщиной не менее 6 мм ...",
            "customer": "МФТИ", "internal": true, "status": "внутренний стандарт заказчика", "score": 50.131, "...": "..."}]}
```

## Форма 5: история

### GET /api/runs?user=&limit=50&offset=0

Карточки по времени, новые сверху. В историю попадают и прошлые запуски (до появления истории): у них пустой `user`, дата по времени отчёта, группы все три. Сравнения версий `/compare` (без отчёта) в историю не попадают.

```json
{"total": 9, "items": [
  {"number": 6, "run_id": "871f5ff20a73", "kind": "check", "created_at": "2026-11-14T16:59:02", "finished_at": "2026-11-14T16:59:04",
   "user": "Иванова", "seconds": 1.9, "files": ["lift_src.docx"], "previous_file": "",
   "checks": ["logic", "standards", "risks"], "check_groups": ["Логика", "Стандарты", "Риски"], "full_check": true,
   "mode": "rules", "model": "", "orchestrator": "linear",
   "counts": {"total": 18, "by_group": {"Логика": 6, "Стандарты": 10, "Риски": 2}, "by_severity": {"high": 5, "medium": 7, "low": 6},
              "high": 5, "errors": 5, "model_block": 0, "unchecked": 3, "revisions": 9},
   "verdict": "Публиковать без исправлений нельзя: ...", "verdict_code": "blocked",
   "decisions": {"принято": 1, "отклонено": 1, "ручная проверка": 0, "всего решений": 2},
   "links": {"report_json": "...", "comments_docx": "...", "revisions_docx": "...", "result": "/api/runs/871f5ff20a73"}}
]}
```

- `number`: порядковый номер запуска от самого раннего (1, 2, ...).
- `seconds`: длительность запуска.
- «Результаты»: `counts`; «решение»: `verdict` / `verdict_code` и сводка решений закупщика `decisions` (последнее решение по каждому замечанию).
- `kind`: `check` или `requirements_compare` (тогда есть `previous_file`).
- Фильтр по пользователю: `?user=Иванова` (только его запуски).
- Видимость: `TZCHECK_HISTORY_PUBLIC=1` (по умолчанию, демо) история общая; `0`: без `user` список пустой, `GET /api/runs/{id}` и задачи отдаются только с `user` владельца запуска (иначе `404`). Авторизации нет, `user` это имя из формы, а не проверенная личность.

Карточка открывается как форма 3: `GET /api/runs/{run_id}` (`links.result`).

Старые поля и их смысл прежние.

## CLI

```
python -m tzcheck samples/lift_src.docx --no-llm --checks standards,risks -o out
```

`--checks` принимает `logic`, `standards`, `risks` через запятую или `all` (по умолчанию). Рядом с отчётом пишется `<base>.revisions.docx`, если есть точные замены.

## Хранение

- Запуски: `TZCHECK_STORE` (в Docker `/data/runs`, том `runs`), папка на запуск: исходные файлы, отчёты, `run.json` (дата, пользователь, длительность, группы, статус), `req_compare.json` у сопоставления.
- Внутренние стандарты: `TZCHECK_NORMS_CUSTOM_DIR`, по умолчанию `<TZCHECK_DATA_DIR>/norm_custom` (в Docker `/refdata/norm_custom`, том `refdata`, переживает пересборку образа; индекс пересобирается сам при первом поиске после перезапуска).
- Видимость истории: `TZCHECK_HISTORY_PUBLIC` (`1` по умолчанию, `0` только свои запуски по `user`).
- Параллельных задач: `TZCHECK_JOB_WORKERS` (по умолчанию 2), остальные ждут в очереди со статусом `queued`.
